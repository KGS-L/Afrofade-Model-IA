# Afrofade — Configuration Supabase

Ce document décrit la configuration Supabase utilisée par Afrofade en production.

## 1. Architecture retenue

Afrofade utilise **Supabase Auth** comme source d'identité et Supabase PostgreSQL comme base de données.

Flux principal :

```text
Utilisateur
  -> Supabase Auth
  -> auth.users
  -> public.user_profiles
  -> role: customer | salon | admin
  -> données métier + RLS
```

Clerk n'est pas utilisé dans l'architecture actuelle.

## 2. Variables d'environnement requises

Dans le `.env` de production du VPS :

```env
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=<anon-or-publishable-key>
SUPABASE_SERVICE_ROLE_KEY=<service-role-key>
```

Les deux secrets internes suivants sont générés automatiquement au premier déploiement si leur valeur est vide ou encore un placeholder :

```env
API_INTERNAL_SECRET=<auto-generated>
CRON_SECRET=<auto-generated>
```

Ils sont ensuite conservés dans le `.env` du VPS.

### Sécurité

- Ne jamais committer `.env`.
- Ne jamais exposer `SUPABASE_SERVICE_ROLE_KEY` au navigateur.
- Ne jamais copier la `SUPABASE_SERVICE_ROLE_KEY` dans une variable préfixée `NEXT_PUBLIC_`.
- Le fichier `.env` de production doit rester lisible uniquement par son propriétaire (`chmod 600`).

## 3. Où récupérer les clés Supabase

Dans le Dashboard Supabase du projet Afrofade, ouvrir les paramètres API du projet et récupérer :

- **Project URL** -> `NEXT_PUBLIC_SUPABASE_URL`
- **anon / publishable key** -> `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- **service_role / secret key** -> `SUPABASE_SERVICE_ROLE_KEY`

Vérification côté VPS sans afficher les secrets :

```bash
grep -E '^(NEXT_PUBLIC_SUPABASE_URL|NEXT_PUBLIC_SUPABASE_ANON_KEY|SUPABASE_SERVICE_ROLE_KEY)=' .env \
  | sed 's/=.*/=***CONFIGURED***/'
```

## 4. Migrations de base de données

Les migrations doivent être appliquées dans cet ordre :

```text
web/supabase/migrations/01_init_schema.sql
web/supabase/migrations/02_p0_security_commerce.sql
web/supabase/migrations/03_dual_payment_providers.sql
```

### Migration 01

Crée les tables métier principales :

- `salons`
- `subscriptions`
- `hairstyles_catalog`
- `clients_heads`

Elle active également l'extension UUID utilisée par les migrations suivantes.

Vérification :

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
AND table_name IN (
  'salons',
  'subscriptions',
  'clients_heads',
  'hairstyles_catalog'
)
ORDER BY table_name;
```

### Migration 02

Crée la couche sécurité/commerce :

- `user_profiles`
- `payment_transactions`
- `credit_wallets`
- `credit_transactions`
- `credit_purchases`

Elle active le RLS sur ces tables et installe la fonction `finalize_afrofade_payment` réservée au `service_role`.

Vérification :

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public'
AND table_name IN (
  'user_profiles',
  'payment_transactions',
  'credit_wallets',
  'credit_transactions',
  'credit_purchases'
)
ORDER BY table_name;
```

### Migration 03

Étend les paiements afin d'accepter :

```text
money_fusion
genius_pay
```

et recrée la fonction de finalisation afin qu'elle conserve le fournisseur réellement utilisé.

Vérification :

```sql
SELECT
  conname,
  pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conname = 'payment_transactions_provider_check';
```

Le résultat doit contenir `money_fusion` et `genius_pay`.

## 5. Utilisateurs et rôles

Les rôles Afrofade sont :

```text
customer
salon
admin
```

Ils sont stockés dans `public.user_profiles`.

Un utilisateur authentifié sans profil explicite est traité comme `customer` par le serveur. Les rôles `salon` et `admin` doivent être attribués explicitement.

### Lister les utilisateurs et leurs rôles

```sql
SELECT
  u.id,
  u.email,
  COALESCE(p.role, 'NO_PROFILE') AS role,
  p.salon_id,
  u.created_at
FROM auth.users u
LEFT JOIN public.user_profiles p
  ON p.user_id = u.id
ORDER BY u.created_at DESC;
```

### Donner le rôle admin à un utilisateur existant

Remplacer l'adresse e-mail :

```sql
INSERT INTO public.user_profiles (
  user_id,
  role,
  salon_id
)
SELECT
  id,
  'admin',
  NULL::uuid
FROM auth.users
WHERE lower(email) = lower('admin@example.com')
ON CONFLICT (user_id)
DO UPDATE SET
  role = 'admin',
  salon_id = NULL,
  updated_at = NOW()
RETURNING user_id, role, salon_id;
```

### Donner le rôle salon

Un rôle `salon` doit être associé à un `salon_id` valide :

```sql
INSERT INTO public.user_profiles (
  user_id,
  role,
  salon_id
)
VALUES (
  '<AUTH_USER_UUID>',
  'salon',
  '<SALON_UUID>'
)
ON CONFLICT (user_id)
DO UPDATE SET
  role = EXCLUDED.role,
  salon_id = EXCLUDED.salon_id,
  updated_at = NOW();
```

## 6. Authentification Afrofade

Le frontend utilise actuellement :

- OTP e-mail Supabase
- Google OAuth via Supabase

Le serveur vérifie le token Supabase avant de charger `role` et `salon_id` depuis `user_profiles`.

Les routes protégées actuelles sont :

```text
/dashboard
/admin
```

`/admin` nécessite explicitement le rôle `admin`.

## 7. Callback d'authentification

Le callback applicatif Afrofade est :

```text
https://afrofade.pro/api/auth/callback
```

Lors de la configuration des URL Supabase Auth, utiliser le domaine de production Afrofade et autoriser le callback correspondant.

Pour le développement local, ajouter également l'URL locale utilisée par le frontend.

## 8. Paiements

La configuration Supabase est indépendante de la validation commerciale du compte Money Fusion.

En production, le fournisseur activé est contrôlé via :

```env
PAYMENT_ENABLED_PROVIDERS=money_fusion
```

GeniusPay doit rester désactivé tant que son endpoint HTTPS et ses credentials de production ne sont pas validés.

La finalisation d'un paiement ne doit jamais être décidée par le navigateur. Le serveur vérifie le paiement et la base applique la finalisation de manière idempotente.

## 9. Vérification rapide avant déploiement

```bash
grep -E '^(NEXT_PUBLIC_SUPABASE_URL|NEXT_PUBLIC_SUPABASE_ANON_KEY|SUPABASE_SERVICE_ROLE_KEY|PAYMENT_ENABLED_PROVIDERS|MONEY_FUSION_API_URL)=' .env \
  | sed 's/=.*/=***CONFIGURED***/'
```

Puis vérifier dans Supabase :

1. migrations `01`, `02`, `03` appliquées ;
2. utilisateur admin présent dans `auth.users` ;
3. ligne correspondante dans `public.user_profiles` avec `role = 'admin'` ;
4. les utilisateurs salon disposent d'un `salon_id` valide ;
5. RLS activé sur les tables commerce créées par la migration 02.

## 10. Dépannage

### `INSERT ... SELECT` ne crée aucune ligne

Vérifier que l'utilisateur existe réellement dans Supabase Auth :

```sql
SELECT id, email, created_at
FROM auth.users
WHERE lower(email) = lower('user@example.com');
```

Si la requête retourne `0 rows`, créer/inviter d'abord l'utilisateur dans **Authentication -> Users**.

### Un utilisateur admin est redirigé vers `/dashboard`

Vérifier :

```sql
SELECT u.email, p.role, p.salon_id
FROM auth.users u
JOIN public.user_profiles p ON p.user_id = u.id
WHERE lower(u.email) = lower('admin@example.com');
```

Le rôle doit être exactement `admin`.

### Un salon n'a pas d'abonnement reconnu

Vérifier que :

- `user_profiles.salon_id` référence le bon salon ;
- une souscription active existe dans `subscriptions` ;
- le paiement correspondant est `paid` dans `payment_transactions` ;
- `expires_at` n'est pas dépassé.
